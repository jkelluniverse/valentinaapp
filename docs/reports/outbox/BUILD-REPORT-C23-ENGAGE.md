## Discrepancies & decisions needed

1. **The spec asserted an existing property that was false — ruling 12's exact shape, reported rather than worked around.** §"Standing laws" states, as fact, that *"capture records what they used"* (the prospect's language). It did not. `/join` had the submitted `lang` in hand and threw it away; there was no `locale` column at all, and `lib/signup.ts` recorded no language either. §1 only says to add `locale?` "if not already present", so the column was in scope — but the *wiring* was presented as done. I added the minimal wiring (three call-sites: `lib/prospect-capture.ts` stores it on create and on a submission that carries one, `app/(public)/join/actions.ts` passes the `lang` it already read, `lib/signup.ts` stores the signup locale). Capture stays 59/59 and signup 37/37. **Question: ratify the wiring as implementing the spec, or was a locale-less prospect intended to always fall back to English?** (Verify item 6's "defined default" is implemented and proven either way.)
2. **The switches are DB rows with env overrides, and the gate defaults CLOSED.** §"Standing laws" asks for "a feature gate Jacob can close without a deploy, plus a global pause", and §5 asks only that the admin *show* the state. Implemented: `PracticeSetting.engageEnabled` (the gate) and `PracticeSetting.engagePaused` (the pause), each also settable by `ENGAGE_ENABLED` / `ENGAGE_PAUSED`; the pause beats the gate; both are re-read on **every step**, so closing either stops a run in flight. **The gate is closed unless something explicitly opens it** — an automated mailer must not start sending because code shipped, and this matches the existing `autoPayReminders` opt-in precedent. **Question: ratify default-closed and the DB-row mechanism?** No toggle UI was built (that is not in §5, and a send-to-forty-people button next to a table felt like the wrong affordance to invent).
3. **`emails/envelope.ts` gained one optional field.** A plain-text URL in an HTML part is not a working one-click unsubscribe, so the house Envelope now takes `unsubscribe?: {label,url}` and renders a real anchor in the footer plus a line in the text part. Additive and optional: transactional mail passes nothing and renders byte-identically. **Question: ratify touching the shared layout, or should follow-up have had its own?** (I judged a second email layout to be the worse outcome.)
4. **`only=engage` and `asOf=` on the existing tick.** Both behind `JOBS_SECRET`. `asOf` is consumed *only* by the engage step — handing "pretend it is next Tuesday" to a payments sweep is not safe. `only=engage` exists because the harness must tick follow-up a dozen times without auto-completing appointments as a side effect. No second scheduler was created. **Ratify?**
5. **Every message is signed "Valentina" and carries her practice footer.** §3 asks for "signed by a person"; the house Envelope hardcodes her wordmark, tagline and signoff, and its footer line is *"Coaching — not medical or psychological treatment."* That is arguably odd on a platform email to a practitioner, but changing it is a brand-chrome decision, not a follow-up build's. **Flagging, not changing: is Valentina the right sender for practitioner follow-up, or should the platform have its own envelope?**
6. **One-click unsubscribe is genuinely one click, so a link-prefetching mail scanner can trigger it.** §6 forbids a confirmation step, so this is spec-compliant and deliberate; the honest trade is that a corporate scanner that GETs every link will unsubscribe that prospect. The failure mode is "we stop emailing someone" rather than a data loss, which is the right direction to fail. **Flagging for awareness; an interstitial would violate §6 as written.**
7. **Sender-side anchors.** §2 says "same-day" and "immediate" but does not name the anchor. Implemented: `event-lead` counts from the prospect row's `createdAt`, `founding-welcome` from `convertedAt` (falling back to `createdAt`). Proven in the gate.
8. Not built, per "Out of scope": no open/click tracking or any per-recipient telemetry, no SMS, no in-app notifications, no third sequence, no reward mechanism, no second scheduler, no change to any baselined screen.

## Cost / ops notes

- **Migration run:** `47_prospect_message` (`prisma migrate deploy`). **Must be deployed before the engage surfaces or the tick 500s on the missing table.**
- **New env vars, all optional:** `ENGAGE_ENABLED`, `ENGAGE_PAUSED` (either switch also works as a `PracticeSetting` row, which is the no-deploy path). Existing and unchanged: `RESEND_API_KEY` + `NOTIFY_FROM_EMAIL` (both required by `emailConfigured()`), `JOBS_SECRET`, `PLATFORM_DOMAIN`, `PLATFORM_ADMIN_EMAILS`.
- **To turn follow-up on in production:** deploy migration 47, then set `PracticeSetting.engageEnabled = "on"`. Until that row exists, **every due step records `SKIPPED / engine-gate-closed` and nothing sends** — and those rows stay re-sendable, so nobody is silently skipped forever. Read `/admin/prospects` first (queue + dry-run) before opening the gate; the dry-run writes nothing.
- **To stop it:** set `PracticeSetting.engagePaused = "on"`. Takes effect on the next step of the current tick, no deploy.
- **Vendors touched:** none. No new dependency. Resend is reached only through the pre-existing `lib/notify.ts`, and never during verification — the harness injects its own transport rather than stubbing a fake one that reports success.
- **Note for the sequence's own economics:** `PLATFORM_DOMAIN` must be set in production or the signup/portal/unsubscribe links in every message degrade to `PUBLIC_APP_URL` and then to a relative path. An unsubscribe link that is relative is not a working unsubscribe link.
- The scratch DB received exactly one full tick after all gates had passed (nothing was auto-completed or expired: every other counter was 0); the probe rows were removed and `audits/tenant-stamp-audit.ts` reports the same pre-existing 2 rows as before.
