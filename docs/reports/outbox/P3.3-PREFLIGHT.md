## SHAPE QUESTION 1 — the exemption may be unnecessary, and adding it would WEAKEN us

Ruling 122 fixed the transitional exemption at exactly two routes. That was decided
before we knew which hosts those two callers use. **Both use the mapped host**, so both
already resolve through `TenantDomain` after P3.1 — neither needs the fallback at all.

An exemption for them would therefore never fire in normal operation, and the only
case where it WOULD fire is the one we least want to be quiet about: a provider
repointed to an unmapped host. With the exemption, that lands on the default tenant by
host-pattern — a money webhook attributed by accident, which is precisely ruling 113's
prohibition. Without it, that same event refuses loudly, which is ruling 112.

**Recommendation: build P3.3 with NO fallback exemption**, and instead add a gate
assertion that the live callback hosts are mapped — so if someone unmaps
`valentinavelez.com`, the sweep goes red at build time rather than the money path going
quiet at runtime. If the exemption is dropped, ruling 114's companion scanner has
nothing to guard and should be dropped with it; the nexturl-origin scanner and
harness-guard already cover their own ground.

**I did not build either version.** This reverses a ratified decision on a money
surface, and the reversal is only justified by evidence that postdates it.

## SHAPE QUESTION 2 — the gates, and it is the biggest part of P3.3

A2 said gate fixtures belong INSIDE P3.3 and a gate is never relaxed to accommodate it.
The blast radius, measured:

- `audits/tenant-scope-verify.ts` and `audits/nested-stamp-verify.ts` each define
  `DEFAULT_HOST = "localhost:3000"` with the comment *"no PLATFORM_DOMAIN suffix →
  default tenant"* — that comment IS the fallback, and between them they use it on
  ~20 call sites.
- Worse and wider: **most gates never set `PLATFORM_DOMAIN` at all.** Today that means
  `slugFromHost` returns the default slug for every host they use. After P3.3 it would
  mean nothing resolves, and those gates fail wholesale — not because the product broke
  but because the fallback was their implicit fixture.

Two ways to give them an explicit tenant, which is what A2 demands:

- **(a) One migration seeding `localhost` (and `127.0.0.1`) → the default tenant.** Small,
  uniform, and it makes dev and gates resolve through the SAME mapping mechanism
  production uses — explicit data, not a code fallback. Cost: production carries a
  `localhost` row, which is inert but untidy.
- **(b) Each affected gate seeds its own `TenantDomain` row in fixture setup.** Keeps
  production clean and is maximally explicit per gate. Cost: touching 15+ gate files,
  the same kind of sprawl ruling 55 deferred once already.

**Recommendation: (a)**, because it is one reviewable row, it cannot drift per-gate, and
it models exactly what we want everyone to internalise — a host resolves because data
says so.
