# HOTFIX — the platform host's front doors, broken by P3.3 and restored

**I broke psychefolio.com/signup and /join with P3.3, and the 40/40 sweep that
shipped it could not have known.** This is that fix, as its own commit.

## What was broken, and what a visitor saw

Platform host only. `valentinavelez.com` and `{slug}.psychefolio.com` resolve, so
their writes proceeded throughout. Reads on the platform host were fine.

- **`psychefolio.com/signup` — dead.** The page rendered 200, the form submitted,
  and the action redirected to `/signup?…&error=failed` — the generic refusal.
  No tenant, no practitioner, no email. Founding-partner signup from the
  platform's own domain did not work.
- **`psychefolio.com/join` — half broken, which is worse, and this is the
  user-visible harm that justifies fixing it first.** The `PractitionerProspect`
  row **was written**, and the visitor was *then* sent to `/join?…&error=failed`.
  Concretely: a founding partner stands at the event, types their name and email,
  is told it failed, and walks away — while their row sits in the database.
  Nobody follows up, because the row looks like every other captured lead; and
  they do not try again, because they were told it did not work. The lead is not
  lost in the database. It is lost in the world.

## The mechanism, from the server's own log

```
[tenancy]      UNRESOLVED host "psx.localhost" — no TenantDomain row and no {slug}.$PLATFORM_DOMAIN pattern
[tenant-scope] refusing scoped access: host "psx.localhost" …
[signup]       provisioning threw tenant-scope: … scoped data access refused
[capture]      failed tenant-scope: … scoped data access refused
```

The scoped client's proxy resolves a tenant **only for models in
`SCOPED_MODEL_SET`** (`lib/prisma.ts:358`) and passes unscoped models straight
through. That is precisely why the failure had the shape it did, and the shape is
what made it diagnosable:

- in **capture**, `PractitionerProspect` (unscoped) succeeded and `AuditEvent`
  (scoped) threw — hence a written lead behind an error screen;
- in **signup**, `Tenant` and `TenantModule` (unscoped) succeeded, then
  `TenantBilling` (scoped) threw and the rollback removed everything.

P3.3 made an unresolvable host refuse all scoped access. Right for touching a
practice's data. Wrong for operations that are platform-level and **already state
their own `tenantId`** — they never needed the request's tenant, they were
borrowing it. Before P3.3 that borrow silently returned Valentina.

## A1 / A2 — the classification, settled before a line was written

The instruction was explicit: if any of the three is genuinely tenant-scoped and
merely looks platform-level, reaching for the raw client re-opens P3.3's hole in
a new place. So each was classified first.

**1. `lib/provisioning.ts` — TENANT-CREATING.** Not "mixed" in the dangerous
sense, and that distinction is the whole argument.
- Platform-level rows: `Tenant`, `TenantModule`.
- Tenant-scoped rows: `TenantBilling`, the practitioner `User`, and on a DEMO
  seed the client `User`, `ConsentGrant`, `ClientProfile`, `LogEntry`.
- **Every one of those scoped rows carries the newly created tenant's id, stated
  literally in the payload. Not one belongs to the requester's tenant.** The
  tenant they belong to does not exist until this function creates it, so
  resolving the operation against the request's host is a category error rather
  than a limitation. The raw client cannot re-open P3.3's hole here because this
  module never derives a tenant from a host at all.
- **A pre-existing defect fixed on the way past:** the duplicate-email check is a
  read that is *meant* to be global — sign-in is by email across tenants — and
  under the scoped client it only ever saw the request tenant's users. Masked
  because `lib/signup.ts` does its own global check with the raw client.

**2. `lib/billing/provision.ts` — TENANT-SCOPED, TENANT STATED BY THE CALLER.**
One row type, `TenantBilling`; read and write both key on `args.tenantId`.
Callers: `lib/provisioning.ts` and `audits/billing/b3-verify.ts`. It never
consults the host and never should.

**3. `lib/prospect-capture.ts` — GENUINELY MIXED, and it does not get a blanket
raw client.**
- Platform side: `PractitionerProspect` — findFirst, findUnique, upsert. Not a
  scoped model; a founding-partner lead belongs to the platform.
- Tenant side: **exactly one row** — `AuditEvent.create`, whose tenantId came
  from the request's host.
- One write changed. Everything else in that file still goes through the scoped
  client.

## A3 — how 40/40 passed while the front door was broken

**No gate had ever performed a write on the platform apex.**
`audits/signup/verify.ts` runs at `http://localhost:3123` and aims its hosts at
`{slug}.platform.test` — tenant subdomains. `audits/capture/verify.ts` submits
`/join` to `localhost`, which the P3.3 fixture maps to tenant #1; it names
`PLATFORM_DOMAIN` only in its env block. **Every write-exercising gate ran on a
host that resolves to somebody.**

Before P3.3 that gap was invisible, because the fallback *guaranteed* every host
resolved to somebody. P3.3 made *which host* load-bearing for writes, and the
gate set had no platform-host write coverage — so **40/40 was true and completely
uninformative about the front door.** The missing coverage is the durable defect;
the code was the symptom.

`audits/platform-frontdoor-verify.ts` is that coverage, and it is the first gate
in this program to write on the platform host. Building it is what found the
outage.

**It needed a correction to become an instrument** (rulings 125/130, a fourth
time). Its first version spoofed `x-forwarded-host` on a browser sitting at
localhost. **Next refuses a server action whose `Origin` and `x-forwarded-host`
disagree**, so the POST was silently dropped and the page landed back on
`/signup` with no query at all — indistinguishable from a mail failure. It now
sits on a real `*.localhost` platform host, where the two headers agree by
construction.

## What was built

**The category correction.** `lib/provisioning.ts` and `lib/billing/provision.ts`
use the raw client, allowlisted with their reasoning in `scripts/guard-prisma.ts`
and `docs/PRISMA-ALLOWLIST.md`. Not a bypass: the comment in each file states the
category and why the host has no business in it.

**The tracked constant (ruling 133).** `lib/prospect-capture.ts` gains
`PLATFORM_CAPTURE_AUDIT_TENANT`, module-local and unexported, used at exactly one
site. A practice's own `/join` still attributes its capture to that practice —
the request resolves and its tenant is used, exactly as before. Only the platform
host, where P3.3 correctly refuses because there is no practice there, reaches
the constant. Its comment says in plain words that this attributes platform
capture rows to tenant #1, that it is wrong, that it is ruling 82, and that P4
item 5 fixes it.

**Two new gates, standing set 40 → 42.**

`audits/platform-writes-verify.ts` — counts, per ruling 128:
1. all **8** scoped writes across the three modules state `tenantId` literally;
2. the ruling-133 constant has exactly **1 definition + 1 use**, is unexported,
   and appears in no other platform-level module;
3. all three modules still import the raw client.

`audits/platform-frontdoor-verify.ts` — live, on a real platform host: signup
completes and mints the tenant, `/join` captures **and** the visitor is not told
it failed, and **no mail leaves that host under a borrowed identity** (C27: sends
as no one, never as someone else).

## Demonstrated able to fail — four directions

| Injected defect | Gate | Result |
| --- | --- | --- |
| a scoped write loses its `tenantId` | platform-writes | ✗ `MISSING: lib/billing/provision.ts: tenantBilling.create`, exit 1 |
| the tracked constant gains a second use | platform-writes | ✗ `3 occurrence(s)… expected exactly 2` |
| a module returns to the scoped client | platform-writes | ✗ `lib/billing/provision.ts imports the raw client` |
| **the actual outage, reintroduced** | platform-frontdoor | ✗ `SIGNUP COMPLETES… — NO TENANT · landed=/signup?…&error=failed`, exit 1 |

The last row is the one that matters: reverting a single module to the scoped
client reproduces the exact production symptom, and the new gate catches it. In
that run `/join` stayed green, which is correct — the capture fix lives in a
different module, and the gate is precise about which door broke.

## RULING 136's SURVEY — "global by intent, scoped by accident", the rest of the class

`User.email` is `@unique` in the schema — **globally unique across every
tenant**, because sign-in is by email. Any "is this email taken?" read performed
through the scoped client therefore asks a narrower question than it means to.
The scoped client rewrites `findUnique` into `findFirst` with a tenant filter, so
it answers "not taken" for an email that IS taken in another practice; the write
then hits the database's unique constraint and the person gets a generic failure
instead of "that address is already in use".

**Fixed by this hotfix (1):** `lib/provisioning.ts`'s duplicate-email check,
which is now global with the raw client.

**Found, NOT fixed — out of a hotfix's scope, named so they are tracked (3):**

| Site | The question it means to ask |
| --- | --- |
| `app/account/actions.ts:86` | is the requested new email already somebody's login? |
| `app/account/confirm-email/[token]/page.tsx:20` | the same check, at confirm time |
| `app/invite/[token]/actions.ts:29` | does this invitee already have an account? |

None is a data-integrity breach — the unique constraint holds either way — but
each produces a wrong answer and a confusing failure, and the invite one can
strand an invite. They want one fix together, not three scattered ones.

**Examined and judged CORRECT as they are**, so the class is not left vague:
`app/forgot/actions.ts:29` (a reset request on a practice's host should not
confirm that an address exists in a different practice), and the token lookups by
`tokenHash` — `passwordResetToken`, `emailChangeRequest`, `invite` — where the
token carries its own tenant and scoping means the link works on its own host.
Noted rather than changed.

## THE DIAGNOSTIC ROW — A CORRECTION, AND NO SQL IS NEEDED

`PractitionerProspect` `cmu8ntxwn0001kqgsi05bgsoy` is **not production data.** It
was written to the local **scratch** database by
`audits/platform-frontdoor-verify.ts`, which refuses a Railway `DATABASE_URL`
outright (`if (/railway|rlwy\.net/.test(url)) throw`) and runs only against
`postgresql://…@localhost:5432/veritas_scratch`. Its own `cleanup()` removed it,
and I re-queried to be sure rather than assuming:

```
select id, email, status from "PractitionerProspect"
  where id='cmu8ntxwn0001kqgsi05bgsoy' or email like 'p4-%';   -- 0 rows
select count(*) from "AuditEvent"
  where action='prospect-capture' and "actorId"='cmu8ntxwn0001kqgsi05bgsoy';  -- 0
```

**There is nothing for Jacob to confirm or delete, and no orphaned AuditEvent
exists** — in the broken state the audit write was exactly what threw, so no row
was ever created for it, in any database. I have deliberately not drafted the
confirm/delete statements, because handing over SQL that targets a row which does
not exist in production invites running it there.

## What this fix deliberately does NOT do

- **It does not restore the welcome email on the platform host.** That send is
  still skipped, and correctly so today: no caller passes `platformIdentity()`,
  so `notify.ts` skips rather than borrows a practice's letterhead. P4 item 1
  routes platform paths through the platform identity. The gate reports the
  absence rather than asserting it, so the file stays honest instead of soft.
- **It does not fix the attribution.** Platform capture audit rows still land on
  tenant #1. That is ruling 82, now named and counted instead of invisible.
- **It does not touch P3.3.** The keystone stands: the `unresolved` flip is
  re-verified live below.
