# C24.1-TENANT-SCOPE — close the class, close task #75

**Spec:** C24.1-TENANT-SCOPE · **Depends-on:** C24-NESTED-STAMP (`lib/tenancy/stamp.ts`, migration 48, `audits/nested-stamp-verify.ts`)
**Priority:** high — finishes the only genuine integrity defect in the program. Needs nothing from Jacob.
**Architect:** decided 2026-09-05, implementing ruling 24.

## Why this exists

C24 fixed the nested-write gap and found that it was not the actual leak. The real mechanism is the scoped
client's **out-of-request passthrough**: `lib/prisma.ts` resolves the tenant from `headers()`, which throws
outside a request, so a CLI write passes through unstamped. Two harnesses were producing null-tenant rows;
C24 fixed one and correctly refused to blind-edit the other, which it could not run.

Ruling 24 ratified **option 1** as the class fix: an opt-in scope that the client consults only when
`headers()` is unavailable. Ruling 24 also **rejected** the alternative of implicitly stamping out-of-request
writes with the default tenant, and the reasoning binds this build: that would remove most of the audit's
detection surface and silently record a second practice's forgotten rows as Valentina's. Do not drift toward
it for convenience. **A quiet defect in the tenancy wall is worse than a loud one.**

## Assumptions to verify, not trust

*(Ruling 18. Each line is the Architect's belief, not a fact. Test it; if it is false, say so and adjust
rather than working around it. C24 disproved this section's central claim last cycle — that was a success.)*

1. `AsyncLocalStorage` from `node:async_hooks` is available and safe in every context this codebase runs a
   scoped write from: Next server runtime, `tsx` CLI scripts, and the job tick route.
2. `lib/prisma.ts` resolves the tenant in exactly one place, so a single fallback consult covers every write
   path — including the array-form `$transaction` builder C24 had to wire separately.
3. The only remaining in-repo producer of null-tenant rows is `audits/remarkable-recording/verify.ts`. C24
   attributed per-gate over the full regression list; **re-confirm rather than assume**, because C24's sweep
   could not run the three credential-gated gates.
4. `audits/remarkable-recording/verify.ts` cannot run in this environment (it needs AssemblyAI). Confirm
   this, because it determines what you may honestly claim about it.
5. `lib/pattern-library.ts` and the other ~9 files that stamp explicitly at call sites do so **because** of
   this same CLI seam, and will keep working unchanged once the scope exists — their explicit values must be
   preserved, never overridden.

## Standing laws this build must honor

- **Server-side enforcement (law #5)** — the mechanism must make correct behavior the default for future CLI
  code, not a thing to remember.
- **Attributable audit (law #6)** — no narrowing of what the audit checks, ever.
- **Kill-switch thinking** — this touches every write in the app. If the scope is absent, behavior must be
  exactly what it is today: passthrough, visible to the audit. Absence of the scope must never become a
  silent default-tenant stamp.

## Build order

### 1. `withTenantScope(tenantId, fn)`

In `lib/tenancy/` — an `AsyncLocalStorage`-backed scope. `lib/prisma.ts` consults it **only** when the
request-header path is unavailable, in this precedence:

1. request tenant from `headers()` — unchanged, always wins
2. else the `withTenantScope` value, if the code is running inside one
3. else today's behavior exactly: passthrough, unstamped, visible to the audit

An explicit `tenantId` in a payload still wins over everything, at any nesting depth — C24's verify item 5
property must survive this build unchanged.

### 2. Adopt it in the harnesses that can be verified

Wrap the CLI harnesses and any CLI-invoked product path that writes scoped models. `prisma/fixtures/c12x-verify.ts`
already states its tenant explicitly — leave that working; the scope should make the belt-and-braces
unnecessary without breaking it.
