## 2. Findings

### P1 — Fresh-database migration ordering is broken — ✅ FIXED IN REPO (prod reconcile pending)
**Resolution (2026-07-14):** folders zero-padded (`00_*` … `18_*`); proven on a
fresh DB — `migrate deploy` applies all 19 in order (47 tables) where it
previously failed with `42P01`, and the prod-simulation confirms the one-time
ledger reconcile makes an existing deployment a no-op. Operator step remaining:
run `scripts/reconcile-migration-names.sql` on production (after backup) before
deploying the renamed folders — see `scripts/migration-reorder-runbook.md`.

**Evidence:** `prisma/migrations/` folder names used *unpadded* numeric prefixes
(`0_`, `1_` … `10_` … `18_`). Prisma applies migrations in **lexicographic**
order, so the real apply order is `0_init → 10_c12 → 11_c13 … → 18_c17 → 1_c1 →
2_c2 …`. `10_c12_integrative` runs **before** `1_c1_accounts` exists →
`42P01 relation … does not exist`. Reproduced: `prisma migrate deploy` on a
fresh DB fails; staging had to be bootstrapped with `db push` as a workaround.

**Impact:** Production is *unaffected* (migrations were applied incrementally,
one at a time, so they went in creation order). But **every fresh environment
fails**: disaster recovery, a new staging box, `prisma migrate reset`, and any
new developer's first `migrate deploy`. This is a latent DR/onboarding landmine.

**Remediation (do carefully — it touches the applied-migration ledger):**
zero-pad every folder to a fixed width (`00_init`, `01_c1_accounts`, …
`18_c17_deepening`). Because Prisma matches applied migrations by folder name in
`_prisma_migrations.migration_name`, renaming on an environment that already ran
them requires a paired `UPDATE _prisma_migrations SET migration_name = …` (or
`prisma migrate resolve`) in the **same** deploy, or the renamed folders read as
brand-new and re-run. Recommended sequence: (1) rename folders in the repo,
(2) ship a one-time SQL data-migration that renames the rows in
`_prisma_migrations` on production, (3) verify a *fresh* `migrate deploy`
succeeds end-to-end in staging before merging. Until then, document `db push`
as the fresh-env bootstrap in `STRUCTURE.md`.

### P2 — Crisis alerts are not deduplicated per client
**Evidence:** `app/practitioner/messages/page.tsx` renders one banner row per
*flagged message* (`crisisMessages.map(...)`), with no per-client grouping and
no snippet or timestamp. Screenshots `m-12`, `d-13`, `m-31` show *"Mira Chen
reached out in distress…"* stacked **twice, identically**.

**Impact:** A client in acute distress very often sends several messages in a
row — which is *precisely* the moment this code path fires — so the practitioner
is shown a wall of identical, context-free alerts. The repetition also dilutes
the signal it's meant to sharpen. (In staging the duplication came from a seed
double-run — P3-5 — but the product-level gap is real regardless.)

**Fix:** group flagged messages by `clientId`; render one row per client with
the most-recent flagged snippet + relative time, e.g. *"Mira Chen · 2h ago —
'…everything feels pointless…' — shown crisis resources; check in."* Patch in
Appendix A.

### P2 — On the First Map, the map is below the fold
**Evidence:** `m-24`. On 390×844 the canvas starts at ≈830 px — the entire first
viewport is eyebrow + title + a five-line paragraph + Arrange/Connect toggle +
an instruction line. The client lands on their *living map* screen and sees no
map until they scroll.

**Impact:** Fails the charter's first-viewport test on the feature's own screen;
the emotional payload ("this is *yours*, it's alive") is buried under
instructions. **Fix:** compress the preamble to a single line (move the long
paragraph behind a small "ⓘ about your map" affordance), and lift the canvas so
at least its top third is visible on first paint.

---

### P2 — Interactive map canvas underlaps the fixed bottom nav
**Evidence:** `m-24`. The canvas extends beneath the fixed tab bar; the lowest
star ("Going cold when dismissed") sits at the nav's edge. Because this is a
drag surface, targets in the bottom ~72 px collide with the nav's thumb zone.

**Impact:** Low stars are hard to grab; drags initiated near the bottom risk
hitting nav items. **Fix:** reserve the nav height as bottom padding on the
canvas container (`pb-[calc(72px+env(safe-area-inset-bottom))]` or shorten the
canvas), so no interactive content lives under the bar.

---

### P3 — Login: empty brand void + borderless fields
**Evidence:** `m-02`. Large blank area above "WELCOME BACK" (no wordmark on the
one screen every user starts from); email/password fields have no visible
border — white-on-cream fill is the only affordance, and there's no visible
focus ring for keyboard users (brushes WCAG 2.4.13 Focus Appearance).
**Fix:** add the `veritas ✦` mark, give fields a `border border-line` + a
`focus:ring-2 focus:ring-wine` state.

### P3 — Bottom nav clips its 5th item at 200 % text
**Evidence:** `m-31`. At 200 % zoom the practitioner nav shows Today/Clients/
Messages/Calendar but "More" is pushed off-screen right; the bar doesn't
reflow. **Fix:** let the bar shrink label size / icon-only below a width
threshold, or make the overflow item collapse into ⋯ deliberately.

### P3 — Desktop messaging is single-column — ✅ ACCEPTED BY DESIGN
**Evidence:** `d-13`. On 1440 px the inbox is a single ~915 px column; opening a
thread navigates away (no two-pane split). This is the deliberate AMENDMENT-04
"the route *is* the thread" model — native-mobile grammar carried to desktop.
**Ruling (2026-07-14): accepted by design.** The single-column, one-thread-per-
route model is intentional and stays as-is on every viewport; the widescreen
"waste" is the cost of one consistent messaging grammar, and we're keeping it.
Not a defect, not scheduled for change.

### P3 — Client Sanctuary hero floats high
**Evidence:** `m-20`. The greeting/quote/CTA cluster sits in the upper ~55 %;
the lower ~45 % is empty cream. Calm-by-design, but slightly unanchored on tall
devices. **Optional:** vertically center the cluster or add a whisper-weight
"today" anchor low in the viewport.

### P3 — Map physics as an INP / main-thread cost
`ConstellationMap.tsx` runs a hand-rolled `requestAnimationFrame` force
simulation. On low-end mobile a continuous rAF loop is an INP risk (good = <200
ms). **Confirm** the loop quiesces (stops rAF when node velocities ≈ 0) rather
than spinning forever, and pauses under `prefers-reduced-motion`.

### P3 — Seed hygiene (staging only, not shipped)
`prisma/staging-seed.ts` uses `message.create` (non-idempotent), so re-running
the seed duplicated Mira's crisis message and Jacob's Moments (visible as "4"
unread and doubled entries in `m-15b`). Make message/appointment/reflection
seeds upsert-by-natural-key or `deleteMany` the client's rows first. Harmless to
production; fix so staging screenshots aren't misleading.

## Appendix A — Patch: dedup crisis banner

In `app/practitioner/messages/page.tsx`, after the `crisisMessages` query,
collapse to one row per client with context:

```ts
// One alert per client — most-recent flagged message, with snippet + time.
const crisisByClient = new Map<string, (typeof crisisMessages)[number]>();
for (const m of crisisMessages) {
  const k = m.conversation.clientId;
  if (!crisisByClient.has(k)) crisisByClient.set(k, m); // query is desc by createdAt
}
const crisisRows = [...crisisByClient.values()];
```

Render `crisisRows` instead of `crisisMessages`, and add the snippet + time:

```tsx
<span className="font-semibold text-rose">{displayName(m.conversation.client)}</span>{" "}
<span className="text-whisper">· {relTime(m.createdAt)}</span> — reached out in
distress: <span className="italic">"{m.body.slice(0, 60)}"</span> — shown crisis
resources; please check in.
```
